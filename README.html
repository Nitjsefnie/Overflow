Overflow cooperative ledger guide

Credit with visible proof.

In brief — Overflow records explicit offers, linked GitHub completion evidence, and a credit transfer between a repository sponsor and an outside contributor.
Overflow is already running at overflow.nitjsefni.eu. Pointing you at that instance is what this repository is for. You do not need to deploy anything to use Overflow — sign in there and join the ledger that already exists. The setup instructions further down build a development environment for changing Overflow itself; they are not the way to use it.

Join the running instance

  1. Sign in. Open overflow.nitjsefni.eu and choose Sign in with GitHub. That is the whole account setup — there is nothing to install and nothing to configure.
  2. Register a repository you administer. Use Register a repository and submit one owner/name or canonical GitHub URL. Registration is explicit and one at a time, and GitHub must report you as an administrator of that repository.
  3. Choose the repository’s catalogs. The opening catalog is the set of offered: labels the repository prices work with, in its own vocabulary; the actual catalog maps each point from 1 through 10 onto a settlement label. The words are yours, the point scale is shared.
  4. Label the work. Apply an opening label when you file an issue, before anyone is assigned, and settle it between the closing pull request’s final commit and its merge with a label and a comment naming that label. Those labels are the ledger’s input, not decoration.
  5. Read the ledger. A signed-in member gets Ledger, Issues, Settlements, Calibration and Rules, and the in-product rules page states the same rules this guide does.

Closing work needs no repository of your own. Take an issue in a repository that is already registered, and the settlement lands in your ledger when the pull request merges and the issue owner settles it — if you have not signed in yet it waits as an unclaimed settlement until your GitHub identity is claimed.

Repository catalogs and headroom

Repository registration is explicit and one at a time. The signed-in person submits one owner/name or canonical GitHub URL and must hold GitHub administrator permission for that repository.

Opening catalogs are entirely repository-chosen: S/M/L can work, as can moonlit ridge, risk: high, or another local vocabulary. Every opening label has comparison and reserve points from 1 through 10. Every actual catalog must contain exactly one editable label for each point from 1 through 10.

The dashboard reads materialized ledger entries. Available headroom is settled balance − reserved points for open issues assigned to outside contributors, and negative headroom remains visible. This release enforces no credit floor and exposes no floor configuration; optional group floors await a later idempotent assignment-enforcement design.

GitHub GraphQL closedByPullRequestsReferences is the only closing-link authority. Opening difficulty comes from the earliest configured label the issue owner applied before the first assignment. Settlement requires an owner-applied issue label between the closing pull request’s final commit and merge plus a nonblank owner comment in that window naming the label. Pull-request labels never price work. Event and comment IDs, actors and times, the exact merge commit OID, and the diff fingerprint remain available as proof.

Scoring, self-work, and moderation

credits = max(0, actual points − distinct review rounds)

There is no churn metric. Calibration compares paired self-work samples with outsider settlements. Self-work becomes calibration evidence but creates no ledger entry. Work by an outside contributor who has not yet signed in remains an unclaimed settlement until their GitHub identity is claimed.

audit → warn → recalibrate → ban

Moderation is account-level and evidence-led: open an audit from paired samples, warn when the evidence warrants it, require recalibration before reactivation, and ban only after confirmed patterns persist.

Running your own instance is not the way to use Overflow

Everything from here on is for people changing Overflow’s code or operating a deployment. The instructions are accurate and contributors need them, but what they build is a development environment, not a route to using Overflow.

Each instance keeps its own ledger. Balances, reserves, settlements, proof records and calibration history live in that instance’s own PostgreSQL database, and nothing in this codebase moves them between deployments. A second instance therefore starts empty and stays private to itself: no registered repositories, no counterpart to settle with, and no credit that anyone else can see or honour. Signing in at overflow.nitjsefni.eu is what puts your work in a ledger other people are already reading.

Development setup

These steps stand up a local copy for working on Overflow itself.

  1. Copy .env.example to .env and replace every placeholder. Generate AUTH_SECRET with npx auth secret; make TOKEN_ENCRYPTION_KEY from 32 random bytes encoded as unpadded base64url.
  2. Use an already-installed PostgreSQL 17 instance, or start the supplied Compose service.
docker compose up -d postgres
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm dev

Run the project gates with pnpm test --run, pnpm lint, pnpm typecheck, and pnpm build.

Operating an instance: GitHub OAuth and webhooks

This section is operator configuration for a deployment you run yourself; on the running instance it is already done. https://<public-host> is a placeholder for your own deployment’s origin — replace it with that origin, and do not read it as an address to visit.

Configure the GitHub OAuth callback as https://<public-host>/api/auth/callback/github. The application needs a public HTTPS GitHub webhook URL and a shared secret:

APP_URL=https://<public-host>
GITHUB_WEBHOOK_URL=https://<public-host>/api/github/webhooks
GITHUB_WEBHOOK_SECRET=<github-webhook-secret>
GitHub must be able to reach the webhook over public HTTPS. Keep the secret private and configure the same value in GitHub and the application.

One repository or all repositories

Webhook processing updates materialized state incrementally. Use reconciliation after webhook downtime or a GitHub configuration change to recover linked issues, pull requests, settlement proof, self-work calibration, and unclaimed contributors.

# One explicit registered repository by owner/name
pnpm reconcile -- --repository <owner>/<name>

# Every active registered repository
pnpm reconcile

PostgreSQL serializes each repository from snapshot collection through materialization. Eligibility is reconstructed at merge time from immutable moderation history, so later sanctions do not rewrite eligible historical settlements or calibration.

Continuous integration

GitHub Actions runs the complete gate on pushes to main, pull requests targeting main, and manual dispatches. With pinned Node, pnpm, and action revisions, it applies migrations to PostgreSQL 17 and runs pnpm test --run, pnpm lint, pnpm typecheck, and pnpm build. A separate actionlint/zizmor workflow validates and security-checks the workflow definitions. Checkout credentials are not persisted.
