03

Decision 1 — how a link is verified

Decision
The link credential is a user-supplied personal access token (PAT).
Per-instance OAuth app registration does not scale: every self-hosted instance would need its own OAuth application registered before a single link could be verified there, and instances the operator does not control cannot be registered at all.
A PAT cannot be obtained for an account the linker does not control — a PAT is created signed-in as that account, on that instance. This is what makes linking a verified credit-claiming action rather than an assertion.
The same credential serves the reconciliation reads afterwards. The probe live-verified that reconciliation reads of comments and label events REQUIRE a PAT anyway — gitlab.com returns 401 unauthenticated for notes, resource_label_events, discussions, and search, across four unrelated projects. The verification credential and the reconciliation credential are the same object.

Verification mechanics

At link time the server performs an authenticated GET {instance_url}/api/v4/user with the submitted token. On success the returned id and username are frozen as (forge_user_id, forge_login) — never re-resolved from the mutable login afterwards — and verified_at is stamped. Minimum scope: read_api (the probe's doc fetch confirms read_api grants read access to the API; read_user is NOT sufficient for project-scoped evidence endpoints). The token is encrypted at rest with the mechanism already used for users.encrypted_oauth_token. PATs are issued by a single instance and carry no cross-instance authority, so the stored (instance_url, token) pair is namespaced by construction.

Re-verification

A 401 on a reconciliation read against a linked identity marks that identity unverified and excludes it from credit resolution until re-verified. This is fail-closed in the same direction as the timeline-completeness apparatus.

Honest boundary: webhook setup is a maintainer configuration step on the target project (probe, DOC) — the PAT makes the account's identity and its reconciliation reads possible; webhook configuration additionally requires the maintainer role on that project and is a separate act.

Decision 2 — why GitLab cannot price review rounds today

GitHub semantics first, precisely, from the enumeration (current tree).

GitHub: a round is one review submission whose effective state at the merge instant was CHANGES_REQUESTED, submitted strictly before merge (review.submittedAt < mergeTime), and not dismissed before merge. Distinctness is per review id, not per reviewer — reviews deduplicate into a map keyed by review id; reviewer identity is never fetched. A DISMISSED review still counts if its previousReviewState was CHANGES_REQUESTED and the dismissal happened at/after merge; a pre-merge dismissal withdraws the round. Count feeds credits = max(0, settled_points − review_rounds). The round exists because GitHub exposes a structured, reviewer-attributed, re-fetchable record of change-request submissions and dismissals, so the fold can recompute it at any later run.

What GitLab exposes falls short on all three properties

  • No changes-requested concept exists (probe; the approvals surface carries approvals only, no review states).
  • Retractions are either unattributed or unstructured. The unapproval webhook action fires when a user removes an approval “either manually or by the system” (webhook doc, live-fetched by the probe) — the action itself conflates the two. System-initiated resets (approvals_reset_on_push) are distinguishable in the payload (system: true), but reset-on-push is a Premium/Ultimate feature enabled by default — attributed to the approvals-settings doc live-fetched during this round's adversarial verification, not to the probe's tier notes — and the grounds that the reset's payload user is the PUSHER and that the reset path writes no system note at all are DOC-VERIFIED the same way (fetched webhook doc + source), not observed live. REST system notes, where they exist, are prose bodies — and the probe's own finding stands: note text is presentation, not contract.
  • No approval-event surface carries a stable event id. approved_by is a mutable snapshot with no history (probe); a webhook delivery UUID is transport metadata, not a re-fetchable entity.
Webhook capture cannot substitute. It is forward-only: a captured stream is not re-derivable at a later fold run, which the recompute property requires; it misses everything before registration; and it fails silently (a missed delivery is indistinguishable from an absent event).
Decision
Review rounds price as ZERO on GitLab.
The deduction (credits = max(0, settled_points − review_rounds)) is a GitHub-only adjustment today. Note for later steps: review_rounds.github_review_id bigint > 0 unique cannot be populated from any GitLab surface; schema remains out of scope here.

The pricing asymmetry — real, accepted, recorded

Identical work carrying change-request deductions on GitHub prices without them on GitLab. Every proxy prices wrongly in some direction:

  • Unapprovals as rounds over-price. Author-push-triggered resets are the concrete mispricing: identical approve-then-push-then-merge behavior prices 1 round on GitLab under default settings and 0 on GitHub — tier-conditionally, since reset-on-push defaults differ by tier. Worse, a reviewer-initiated manual unapproval is the counterpart of GitHub dismissing an approval, which prices ZERO rounds on GitHub; counting it would over-price the very behavior GitHub prices at zero.
  • Absence of approval as a round under-prices nothing but prices no rework — many merged GitLab MRs legitimately carry zero approvals; the proxy never detects demanded rework and deducts for it never.
  • Distinct approvers as rounds contradict GitHub's per-review-id semantics — on GitHub two reviewers approving adds no round, so the proxy would over-price exactly where GitHub under-prices by design.
Extension criterion, so a future change is mechanical: the definition extends the day GitLab exposes a structured, reviewer-attributed, re-fetchable approval-event history (REST, with stable event ids). Until then, zero.
05

Decision 3 — whether creditor_id resolves at fold time or freezes at settlement

Decision
Fold time, retroactive.
Creditor resolution is already fold-time today: the fold resolves the author's forge account id to a local account in memory and writes both creditor_id and the forge account id on every run (repository-fold.ts:480-482,1119-1122); no local match writes the row UNCLAIMED with only the forge account id (repository-fold.ts:1143-1152).
GitHub already has a retroactive claim path: claimGitHubIdentity (postgres-store.ts:1454-1522), invoked at every sign-in (src/auth.ts:119), flips past UNCLAIMED rows matching the signing account's forge id to SETTLED or self-work — guarded by merge-time participation eligibility. It does not re-derive the rows; it claims them.

The fold recomputes derived rows per run (the fold_revision machinery forces exactly this). Therefore a newly linked identity participates at the next reconciliation run, and past UNCLAIMED GitLab settlements claim exactly the way GitHub UNCLAIMED rows claim at sign-in.

Guards carried unchanged

  • Resolution matches only the exact triple (provider, instance_url, forge_user_id), never the login.
  • Participation-eligibility-at-merge (the moderation replay) still gates every claim, retroactive or not.
Why frozen-at-settlement is rejected: it would make GitLab semantics diverge from existing GitHub semantics — the same retroactive claim exists on GitHub today, so freezing for GitLab only creates two meanings of one ledger. And linking is a PAT-verified action (decision 1), so the retroactive claim carries exactly the legitimacy of GitHub's sign-in claim. Freezing buys no credit-integrity gain while requiring new exemption machinery inside the fold.

Gaps and hazards

Numbered for reference from later steps. A PARTIAL or NOT SUPPLIED verdict in section 02 is a successful contract outcome — these are the design-around list, not defects of this step.

1 · A GitHub NOT_PLANNED close reason has no GitLab equivalent
The not-planned gate (repository-fold.ts:469, constant NOT_PLANNED) is GitHub-vocabulary and needs a forge-neutral reformulation in later steps. The conclusion rests on five consistent negatives, not one unpreserved description: a REST state_reason field appears on NO probed surface — state_reason_live.json (the live issue object), the probe's issue-list responses (r17/r18/r24), the master REST entity sources (lib/api/entities/issue.rb, issue_basic.rb), doc/api/issues.md@master, and the live GraphQL schema dump all agree on its absence — so field existence grades NOT SUPPLIED on probed surfaces and UNVERIFIED beyond the probe. A duplicate-close link, closed_as_duplicate_of, is live-observed null in the issue's _links; its semantics are UNVERIFIED. The unwritable-closure prose ("No merged GitHub GraphQL closing pull request was found.") bakes GitHub into moderator-facing text.
2 · The 40-hex merge-commit CHECK and the fold regex exclude SHA-256 repositories
db/migrations/007:105-107 requires ^[0-9a-f]{40}$ and the fold's selector re-tests the same regex (repository-fold.ts:761). Newer GitLab instances can run SHA-256; those repos cannot key a settlement today.
3 · registered_repositories.owner_name is globally unique
(001:29) — the same owner/name on two forges collides. An identity key must become (provider, instance_url, project_id).
4 · The claim-ambiguity sentinel can collide with a real GitLab username
The sentinel __overflow_ambiguous_claim__ (src/lib/github/types.ts:12) is safe only under GitHub's login charset rule (types.ts:6-9); GitLab usernames permit underscores, so the sentinel is a legal GitLab username.
5 · Squash-merge SHA duality
On a squash-merged MR the probe live-verified sha == squash_commit_sha != merge_commit_sha. A GitLab gateway must capture all three fields (merge_commit_sha, sha, squash_commit_sha) — either alone is incomplete evidence.
6 · Three timestamp formats must be normalized on receipt
API objects ISO8601 UTC with milliseconds + Z (merged_at, approved_at); commit dates ISO8601 with numeric offsets (committed_date); webhook changes values in YYYY-MM-DD HH:MM:SS UTC shape (not ISO8601).
7 · per_page silently clamps to 100
Live-verified: a 101 request returned 100 rows, no error. Deep collections need keyset pagination (pagination=keyset, cursor live-verified; offset walls are per-instance). Never rely on per_page > 100.
8 · The per-project labels endpoint returned 401 where issues returned 200
One public project, unexplained instance policy. Treat label-catalog existence checks (item 29) as potentially auth-gated per project, and prefer the labels arrays embedded in issue/MR objects (public).
9 · GitLab bot users are real user rows with ids
GitHub's null rule for Bot/Mannequin/Organization actors has no GitLab analog; attribution semantics differ, and the sponsor predicate's login-fallback is calibrated to GitHub account types.
10 · Timeline-completeness witnesses must be RE-DERIVED, not ported
The current witnesses consume GraphQL timeline counts, REST events/comments manifests, node ids, and Link-header pagination — all GitHub-specific, and the subsystem where this repository's hardest defects have occurred.
11 · Claim-path workflow detection is GitHub Actions-specific and cannot port as-is
(item 30) The detection's Actions-YAML matching is structural and unportable, and the 2026-09-11 probe graded the GitLab side NOT SUPPLIED: no in-repo evidence surface for claim automation exists at all. The claim-path check is GitHub-only — a GitLab gateway reports NOT_CHECKED, which warns nothing — and the assignment-event evidence itself is item 10's gap.
12 · Diff representation differs, so proof hashes are never comparable cross-forge
proof_sha256 provenance is forge-local by construction.
13 · Self-hosted reachability maps onto existing columns
unavailable_reason / unavailable_since (016:12-20); no new mechanism needed, but the decline-reason vocabulary is GitHub-worded today.
14 · Assignment-event evidence has no typed endpoint in the probe's inventory
The opening-window bound (item 10) has no verified GitLab supplier; the window needs a GitLab-native source or a reformulated bound in later steps.
