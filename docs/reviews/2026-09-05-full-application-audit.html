IMPORTANTIssue #11
Evidence
src/lib/db/client.ts:13src/lib/fold/postgres-store.ts:172,185,200tests/db/schema.test.ts:1142
Observed behavior and impact

Each successful advisory-lock holder reserves one connection throughout work(), whose queries then borrow from the same pool. Execute work through a correctly scoped reserved connection, or isolate and bound coordinator connections and admission so lock holders cannot exhaust the work pool. Preserve serialization beginning before snapshot collection.

Architecture, data flow, and ownership

Overflow is a GitHub-native mutual-credit application: Next.js serves member UI and HTTP boundaries; Auth.js supplies GitHub OAuth/JWT sessions; PostgreSQL holds registration, credentials, moderation authority, and derived GitHub facts. A pure fold turns closing PRs, ratings, review rounds, and eligibility history into settlements or self-work calibration. SQL views emit equal-and-opposite ledger entries.

A · member → registration

Identity and explicit enrollment

Browser → Auth.js GitHub OAuth → /user identity and token → numeric ID/login/role plus AES-GCM encrypted credentials and JWT. Explicit public/admin-gated registration → labels and webhook → repository/sponsor/label-scheme configuration.

B · signed delivery → collection

One authoritative reconciliation path

Raw-body HMAC → delivery lease/deduplication → awaited full crawl under a repository advisory lock. GraphQL collects issues, label/assignment/comment history, closing PRs, and reviews. REST fetches raw PR diffs, retaining only SHA-256 fingerprints.

C · facts → balances → browser

Atomic materialization

Pure fold + merge-time participation history → one PostgreSQL transaction replacing issues, PRs, links, review rounds, settlements/self-work/unwritable closures, and reconciliation deltas/completion → ledger_entries → balances → account-scoped server projections.

D · moderator → future eligibility

Independent authority and recovery

Moderator → fresh database role → paired cohort snapshot → locked transition → immutable enforcement events → participation as of merge. Manual CLI enters the same reconciliation path, but currently fails at startup (I5).

Interfaces: src/lib/fold/reconcile.ts:6,25; src/lib/fold/repository-fold.ts:26; src/lib/fold/postgres-store.ts:347; src/lib/moderation/service.ts:73. The HTTP 202 currently follows reconciliation completion; it does not acknowledge a durable queued job.

Data authority and recovery boundaries
DataAuthority and recovery implication
Issues, PRs, closing relationships, labels, reviews, diff fingerprintsGitHub-derived, subject to history availability and the identity/temporal findings.
Ledger entries and balancesSQL views over materialized settlements; no separate writable accounting journal.
Repository enrollment, accountable sponsor, difficulty schemeApplication-owned PostgreSQL configuration. GitHub cannot reconstruct sponsors or arbitrary point mappings.
Member identity binding and encrypted OAuth credentialsApplication-owned. Public metadata does not restore grants or encryption keys.
Audits, cohort snapshots, enforcement events and plansApplication-owned authority affecting merge-time eligibility; not rebuildable from GitHub alone.

The design's blanket “rebuildable” database description (docs/superpowers/specs/2026-09-04-overflow-mvp-design.md:7) needs qualification. Application-owned state and the token-encryption key require backups/recovery even if derived ledger tables can be rebuilt.

Security and least privilege

OAuth App versus GitHub App

The OAuth App can satisfy logical explicit registration: application code chooses the submitted repository, verifies administrator permission, and does not enumerate/enroll everything accessible. A public_repo token itself is not restricted to that registered repository. Its broader public-repository read/write authority includes code and hooks, while Overflow needs only a subset. Removing admin:repo_hook was correct because public_repo already covers repository hooks. GitHub OAuth scopes.

A GitHub App offers selected-repository installation, finer permissions, lifecycle events, and short-lived installation tokens. It still needs explicit enrollment, stable numeric-ID checks, public-only validation, and correctly scoped proof collection. Evaluate metadata/read-only source access and minimum issue-label permissions against actual endpoints; avoid default content-write or private-profile authority. GitHub's App/OAuth comparison.

Migration is not an automatic prerequisite. The unnecessary user-scope request is already fixed. Disclose the coarse public_repo grant accurately and finish I1 follow-ups. A GitHub App is a focused next step when smaller grants are required, and an architectural requirement if “explicit registration” means the token must be incapable of accessing any other repository. Changing login product branding alone does not fix C1 or I2–I3.

CI, operations, and test quality

Operational readiness

The service is reachable behind TLS/HSTS and a loopback reverse proxy, but root execution is inappropriate before broader enrollment (I15). The reviewed tree contains no tracked production deployment/rollback/backup runbook, and inspected live paths contained no application-specific periodic repair service. Deployment reports describe successful setup; they are not executable release/restore procedures.

Before production acceptance, demonstrate encrypted backup and restore of enrollment, sponsors, label schemes, immutable moderation history, and secure recovery of the token-encryption key. Private backup storage was not inspected and no production restore was performed, so this report does not assert that backups are absent.

Add a narrow health/freshness signal and sanitized failure categories/correlation IDs. The persisted generic reconciliation error protects secrets but cannot distinguish expired tokens, rate limits, permissions, changed repository identity, or schema failures (src/lib/fold/reconcile.ts:132).

Acceptance gaps in otherwise useful tests

The baseline's 241 tests credibly cover arithmetic, configurable vocabulary, raw signatures, cryptography, fresh schema, ordinary relational transitions, and earlier concurrency/history regressions. Both workflow validators passed locally; fresh remote job provenance was not re-audited. Missing cases cluster around assumptions shared by fixtures and production:

  • Provider mocks: the baseline OAuth test called the unwanted scope least privilege and mocked provider behavior (tests/security/github-oauth-scope.test.ts:16). The newer scope expectation fixes the primary request, not provider email fallback coverage.
  • Distinct actors: history-authority tests keep issue owner and contributor different, missing the same-author case (tests/fold/history-authority.test.ts:45).
  • One repository: contention tests omit enough distinct successful lock holders to exhaust the pool (tests/db/schema.test.ts:1142).
  • Transpiled CLI imports: Vitest bypasses native runtime syntax/import behavior (tests/fold/reconcile.test.ts:10).
  • Fresh-only migrations: applying migrations twice omits committed older-schema upgrades (tests/db/schema.test.ts:34).
  • Canned query results: SQL-string/dashboard mocks cannot independently prove multiple-assignee semantics, real account scoping, or projection consistency (tests/dashboard/queries.test.ts:15).
  • Stable external names: important integration fixtures omit username rename/reuse, repository identity changes, and cross-repository PRs.

Convert the retained nine probes from assertions that bad behavior exists into expected-correct regression tests as each defect is fixed. Add bounded native-process, provider, prior-schema, real-query, sibling-origin, distinct-repository, and browser checks; expanding workflow complexity by itself will not close these gaps.
